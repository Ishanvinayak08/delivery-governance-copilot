# Governance Framework

## Cadence
| Forum | Frequency | Purpose |
|---|---|---|
| Milestone review | At each milestone close | Confirm acceptance criteria met, decide go/no-go for next milestone |
| Weekly self-review | Weekly | Review RAID log, burn-up and open issues; update this repo's own report |
| Retrospective | Per milestone | Capture lessons learned into the roadmap |

## Decision rights
| Decision | Decides | Consulted |
|---|---|---|
| Scope change | Sponsor (via change request issue) | Contributors |
| New governance rule | Sponsor | Reviewer |
| Merge to `main` | Reviewer (one approval + green CI) | Author |
| Release | Sponsor | Reviewer |

## Change control
Any change to charter scope uses an issue labelled `change-request` stating impact on time, effort, risk and quality. Approved changes are recorded in the roadmap and, if architectural, as an ADR.

## Definition of done
Code merged via PR with tests, README/rule table updated, CI green, changelog entry, sample output regenerated if behaviour changed.

## Quality gates
Lint clean (ruff), tests passing, demo runs end-to-end in CI, no real data in repo.

## Escalation
Blocked more than 1 week or milestone at risk: record in RAID log, raise at milestone review with options and a recommendation.

## Reporting
Status is generated by the tool itself on the repo's own issue export where possible (dogfooding).
